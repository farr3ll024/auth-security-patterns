# CLAUDE.md — .NET + SQL Server local dev starter

## What this is

A reusable docker-compose template: SQL Server 2022 + Azurite (blob/queue/
table emulator) + a minimal .NET Web API with EF Core migrations-on-startup
and a DevSeed service that seeds one dev user + API key on first boot.
Meant to be copied wholesale into a real backend repo — swap the models in
`api/AppDbContext.cs` and the seed logic in `api/DevSeed.cs` for the actual
project's domain.

## Run

```bash
cp .env.example .env   # optional, defaults work
make start              # docker compose up --build -d
make logs                 # watch for the DevSeed-printed API key
make down / make clean    # stop / stop+wipe volumes
```
API on http://localhost:8080 — `GET /health`, `GET /users`.

## Important: no .NET SDK or Docker in this dev environment

Whoever last worked on this template (an earlier Claude Code session) had
**no `dotnet` CLI and no Docker available** to compile or run any of this.
If you're a future session working here and you *do* have the SDK: treat
that as a chance to actually validate the C# for the first time, not an
assumption that it already has been.

## Migrations — read this before touching the schema

`api/Migrations/` contains one `InitialCreate` migration, **hand-authored**
(not generated by `dotnet ef`) to match the `User`/`ApiKey` models in
`AppDbContext.cs`, because the SDK wasn't available to generate it properly.
It's believed correct — `Up()` creates both tables with plausible SQL Server
column types, and `Program.cs` calls `Database.Migrate()` on startup so it
should apply automatically — but it has never actually been run against a
real SQL Server instance or compiled by `dotnet build`.

If you have the SDK: run `dotnet ef migrations has-pending-model-changes`
(or just `dotnet build`) first, before assuming the migration is correct or
adding a new one on top of it. If you find it's wrong, regenerate properly
with `dotnet ef migrations add InitialCreate --force` and replace it.

For any future schema change, generate migrations the normal way:
```bash
cd api
dotnet ef migrations add <Name>
```

## Structure

- `docker-compose.yml` — sqlserver (real healthcheck), azurite, api (waits
  on sqlserver's healthcheck).
- `api/Dockerfile` — multi-stage build; runtime stage installs `curl` for
  its own `HEALTHCHECK` against `/health`.
- `api/AppDbContext.cs` — `User`/`ApiKey` models, no navigation properties
  (so no FK relationship is inferred — `ApiKey.UserId` is a plain column).
- `api/Program.cs` — `Database.Migrate()` then `DevSeed.EnsureSeeded()` on
  startup.
- `api/DevSeed.cs` — idempotent (skips if any `User` row exists).
- `api/.dockerignore` — excludes `bin/`/`obj/` from the build context.
